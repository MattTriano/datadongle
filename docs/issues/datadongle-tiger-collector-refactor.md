# Migrate the TIGER collector to the `SourceReader` + family-driver interface

## Motivation

TIGER/Line is the last of the geospatial, fan-out collectors still on the legacy `TigerCollector.collect(spec, force)` shape. Every other source I have touched now conforms to the collector interface in [`docs/spec/collector-interface.md`](../spec/collector-interface.md): a `spec.py` / `client.py` / `metadata.py` / `reader.py`, driven either by the shared `run_collection` or — for fan-out sources whose one-spec-maps-to-many-files shape doesn't fit that contract — a small `run_<source>_collection` family driver (DKAN, Census). I want TIGER on the same footing so that it runs against both `PostgresEngine` and `IcebergEngine`, stages to disk with a bounded memory footprint, and shares the SCD2 semantics and run-tracking every other collector already has.

TIGER is the most involved migration so far, and worth doing carefully, because it is the first collector that combines *all* of the hard cases at once:

- it fans out over **vintages × geographic units** into one table (like Census), but the unit shape varies by layer — national (one file), state (one file per state), or county (one file per county, discovered by listing a directory);
- it discovers its **schema from a downloaded sample file** (fiona), and that schema can drift across vintages, so the table needs a union-of-vintages schema (like DKAN);
- it is the first migrated collector where the **write mode is genuinely data-dependent**: most layers carry a stable ID column (`GEOID`, `LINEARID`, …) and get SCD2, but some (coastline) have none and must fall back to append-only;
- it is **geometry-first** — every feature carries a geometry that must land portably on PostGIS and on Iceberg/Parquet.

## Problem: what the legacy collector couples

`TigerCollector` works, but it entangles the same three axes the interface refactor exists to separate, plus a few TIGER-specific knots:

- **Collection-mode and scope orchestration live in the collector.** `collect` hard-codes the national/state/county dispatch, the per-file idempotency skip, per-file error handling, and the download→parse→ingest loop — all of which is either source-agnostic orchestration (belongs in a driver) or source transforms (belong in a reader).
- **DDL is generated by hand.** `generate_tiger_ddl` builds a `CREATE TABLE` string by downloading a sample, reading its fiona schema, mapping fiona types to PostgreSQL types, and appending SCD2 columns and indexes — PostgreSQL-only, and a parallel implementation of what `TableSchema` + `engine.ensure_table` now do for every other source.
- **There is no `client.py`.** HTTP is split between the collector (streaming zip download, with retries) and the metadata module (directory-listing fetch, no retries). The interface wants HTTP mechanics — session, retries, streaming downloads — owned by a `client.py`.
- **The high-water-mark/skip is PostgreSQL-shaped.** `_already_ingested` and `_already_ingested_county` run `where vintage = … and statefp = … and valid_to is null` against the target, which only works on the physical-`valid_to` Postgres tables, not the Iceberg satellite. (This is the same portability wall I hit on Census — see the decision below.)
- **Geometry handling is implicit.** The collector relies on the parser emitting WKB-hex and the Postgres engine casting text→`geometry`; there is no engine-neutral declaration that a column is geometry with a given kind/SRID.

## Goals and non-goals

**Goals**

- A `TigerReader` implementing the `SourceReader` protocol (schema discovery, write-mode selection, geometry, source transforms) and a `TigerClient` owning HTTP.
- A `run_tiger_collection` family driver: per-vintage schema discovery → union table → per-file staged write session with per-file error isolation.
- Same `TigerDatasetSpec` and `TigerMetadata` (the metadata's rich `list_vintages` / `list_layers` / `list_files` / `get_download_url` API is the discovery path and stays), converged onto the base `DatasetSpec` and the client for HTTP.
- The reader+spec run unchanged on `PostgresEngine` and `IcebergEngine`; geometry round-trips on both.
- Legacy `TigerCollector` and `generate_tiger_ddl` removed; tests re-laid-out to mirror the other collectors, including a hermetic end-to-end run against `IcebergEngine`.

**Non-goals**

- Changing what TIGER stores (raw shapefile columns, lowercased; a `vintage` column; synthetic `statefp`/`countyfp` for county files that lack them) — behavior parity is the target.
- A portable "already-loaded" skip (see the decision below).
- Cartographic-vs-TIGER source changes beyond what the migration needs — both `source="tiger"` and `source="cartographic"` keep working.

## Design decisions

### A family driver, not `run_collection`

Like DKAN and Census, one TIGER spec names many files landing in one table with a union-of-vintages schema and per-file error isolation — which the one-spec/one-table/one-write-session `run_collection` contract doesn't fit. So TIGER ships `run_tiger_collection`, built from the same primitives (the reader, the `Engine` protocol, the tracker). It discovers each vintage's schema, unions them, `ensure_table`s once, then collects each file into its own write session, isolating failures per file.

### Unit = the finest spec narrowing; county URLs are constructible

The reader handles **one file at a time** (like DKAN's per-identifier narrowing); the family driver enumerates units and narrows the spec per unit before calling `read`. The clean insight that makes this fit the protocol: a county file's URL is constructible from its 5-digit FIPS (`tl_{year}_{ssccc}_{layer}.zip`) exactly the way a state file's is from its 2-digit FIPS. So all three scopes narrow the same way — `state_fips=[fips]` (2-digit state, 5-digit county) or `None` (national) — and `read` builds the download URL from the narrowed spec via `metadata.get_download_url`. Directory listing is still needed to *enumerate* which counties exist (in the driver), but not to build URLs.

Per-file error isolation and per-file staging match both the legacy collector's granularity and the choice already made for Census.

### Write mode is resolved from the discovered schema

The interface's default is "non-empty `spec.entity_key` ⇒ SCD2, else Append." TIGER keeps that but adds a documented deviation: when `entity_key` is unset, the reader auto-detects a stable ID column (`geoid`/`geoidfq`/`linearid`/`tlid`/`areaid`, including year-suffixed variants like `geoid20`) from the discovered columns and uses `[id, "vintage"]`; if none is found, it falls back to `Append()`. Because the target table has one uniqueness constraint, the write mode must be consistent across the whole family — so it is resolved once, from the union of every vintage's discovered columns, and used for `ensure_table` and every write session.

### Geometry: declare it, pass WKB-hex through

The reader declares the geometry column in its `TableSchema` as `Column("geom", GEOMETRY, GeometrySpec(kind, srid=4326))`, with `kind` mapped from the fiona geometry type and promoted to the `Multi*` form (shapefiles mix single/multi). The shapefile parser already emits geometry as EWKB-hex; both engines accept that on write (`PostgresEngine` casts `::geometry`; `IcebergEngine._to_wkb` normalizes EWKT/WKT/WKB-hex/WKB → WKB bytes), so the reader passes the parser's output straight through — no geometry conversion in the reader. Layers with no geometry (e.g. `ADDR`) simply declare no geometry column.

### No already-loaded skip (consistent with Census)

The legacy `_already_ingested` skip can't be expressed portably across both engines — the "current rows for this vintage/state" query depends on a physical `valid_to` column and Postgres param/SQL dialect, which the Iceberg satellite (current-version-as-a-view) doesn't share, and the family-driver contract forbids branching on engine type to issue storage-specific SQL. As decided for Census, I'm dropping the skip and relying on SCD2 idempotency: re-collecting an unchanged file is a no-op merge. The trade-off is sharper for TIGER than for Census because the files are large (national roads, block groups), so a re-run re-downloads and re-parses everything even when nothing changed — the mitigation is to collect only the vintages you need, and, for the append-only (no-ID) layers, to avoid re-running at all (a re-run duplicates rows). Worth a portable `distinct_current_values` engine primitive later if the re-download cost proves painful; deferred until measured.

## Implementation outline

- **`spec.py`** — `TigerDatasetSpec(DatasetSpec)` (converge onto the base; drop the duplicate `source` field), keeping `layer` / `vintages` / `source` (`tiger`|`cartographic`) / `resolution` / `state_fips` / `entity_key` / `lowercase_columns` and the `scope`/`states` properties. `generate_tiger_ddl` and the fiona/DDL helpers are removed (moved into the reader as neutral-type mapping, or deleted).
- **`client.py`** — `TigerClient` owning the session, a module-level retry predicate + tenacity backoff, `get_text(url)` (directory listings) and `download_to_tempfile(url)` (streamed to a temp `.zip`).
- **`metadata.py`** — unchanged discovery API, but HTTP delegated to an injected `TigerClient` so there's one HTTP owner.
- **`reader.py`** — `TigerReader` implementing the protocol: `schema` (download a representative sample per vintage, fiona schema → neutral `TableSchema` + synthetic `statefp`/`countyfp` for county scope + `vintage` + geometry), `write_mode` (resolved from the union of discovered columns), `cursor_spec` → `None` (immutable, full-refresh), `read` (download one file → `parse_shapefile` → stamp `vintage`/synthetic FIPS → yield batches → delete temp file), `extract_cursor` → `None`. Fiona-type→`ColumnType` and geometry-kind mappings live here.
- **`driver.py`** — `run_tiger_collection`: per-vintage schema discovery (isolated), union schema, `ensure_table`, enumerate units per scope (national/state/county, county via `list_files` filtered to `spec.states`), then per-unit narrow → write session → `read` → `write_batch`, with per-file error isolation and a family-level summary.
- **Remove** `collector.py`; add a `README.md`.

## Testing

Mirror the other collectors' layout under `tests/collectors/tiger/`:

- `test_spec.py` — validation, `scope`/`states`, entity-key defaults.
- `test_client.py` — retry predicate; streamed download and directory fetch against a mocked session (no live calls).
- `test_metadata.py` — the existing live-site tests stay `@pytest.mark.network` (deselected by default).
- `test_reader.py` — protocol conformance (`isinstance(reader, SourceReader)`), fiona→neutral schema mapping, geometry declaration, entity-key auto-detection, `vintage`/synthetic-FIPS transforms, `cursor_spec is None`.
- `test_driver.py` — end-to-end `run_tiger_collection` against a hermetic `IcebergEngine` (tmp warehouse) with a `NoopTracker`, using **tiny real shapefile zips generated with fiona** so the actual parser and geometry path run: first collect lands features with geometry; re-collect unchanged is a no-op SCD2 merge; a changed feature versions only that row; the state fan-out and county synthetic-FIPS injection land; a failing file is isolated; a no-ID layer collects append-only.

Behavioral invariants to preserve: importing the package touches no network; peak memory is bounded by batch size (streamed download + streamed parse + staged write); a failed file leaves the target untouched; the same reader+spec runs on both engines.

## Open questions / future work

- **Re-download cost without a skip.** Larger for TIGER than for other sources; revisit a portable `distinct_current_values` (or similar) engine primitive if it bites.
- **Divergent auto-detected keys across vintages.** If two vintages in one spec expose different ID columns (e.g. `geoid20` vs `geoid`), resolving the entity key from the union could pick an inconsistent key; in practice a spec's vintages share an ID column, and an explicit `entity_key` overrides. Documented, not guarded.
- **3D geometries.** Mapped to the `*Z` kinds for parity; TIGER is overwhelmingly 2D, so this is largely untested in the wild.
